# Cross references

Which other verses a verse connects to, and one sentence on why. This is the
largest job in the repository, and the only one with two ways of finding the
answer.

**How much is done is in [STATUS.md](../STATUS.md)**, which is generated from the
data. This page is about how to run it.

---

## Two ways to find a reference

Both write `generate/references/<language>/<book>/<chapter>/<verse>.json`, and
the second **merges** into what the first left — `mergeReferences` never removes
anything. So they can run in either order, and the file ends up holding both.

**`generate/references.ts` asks.** The model gets the Hebrew or Greek and
answers from what it knows. It works for every language and all 66 books, on
Claude or with `--local`, and everything currently on disk came from it. It knows
the traditional cross-reference tradition, so the canonical links come out
readily.

**`generate/references-semantic.ts` searches.** `bge-m3` vectors over osnb, the
nearest verses by cosine similarity, then a local model reads the source verse
and each candidate side by side and judges whether the connection is real.

The difference that matters is not the number of references. It is where the
address comes from:

| | `references.ts` | `references-semantic.ts` |
|---|---|---|
| where the target comes from | the model's memory | a verse pulled from the corpus |
| what the explanation is based on | memory of the target | the target's actual text, read in the call |
| can name a verse that does not exist | yes | no, by construction |
| can name a real verse that is the wrong one | yes | no, by construction |

The first row is already handled: `checkTarget` drops an address that lands
outside the book at write time, and `--validate` sweeps the same gate over what
is on disk.

**The second row is not, and cannot be.** A confused book whose chapter and verse
happen to exist — `Høy 105:33` where `Sal 105:33` was meant, but the target
exists in both — produces a live link to an unrelated verse. No structural check
can see it; it needs someone to read the target text. That class is invisible,
probably the largest one left, and searching instead of asking removes it
entirely rather than catching it afterwards.

That is what the semantic pass is for. It is not a top-up on the other script.

`generate/references/en` is generated by neither. It is translated from `nb` by
`translate.ts`, so corrections belong in `nb` and reach English through the
translation run.

## What each one costs

**Searching is not the slow one. Asking the wrong model was.** The semantic pass
defaults to `qwen3.5:122b`, because it passes `task: 'references'` — the same task
name the other script uses. Pin a different judge and the picture changes
completely:

| | s/verse |
|---|---|
| `references.ts --local` | 12 |
| `references-semantic.ts`, default judge (`qwen3.5:122b`) | 96 |
| **`references-semantic.ts`, `OLLAMA_MODEL=qwen3.6:35b`** | **17** |

Five seconds separate the two approaches once the judge is right. For those five
seconds you get an address that came out of the corpus rather than out of the
model's memory.

`bge-m3` is not the judge. It produces the vectors; the candidates it finds are
judged by whatever `taskModels.references` resolves to. The two stay resident
together — adding `--concepts`, which makes four embedding calls per verse, cost
no time, so nothing is being evicted.

### Choosing the judge

`qwen3.6:35b`, pinned with `OLLAMA_MODEL` — the command is under *The semantic
pass* below.

**Why that one, and what the alternatives cost, is in
[running-jobs.md](running-jobs.md)** → *Which judge fits the machine*: resident
memory, seconds per verse and precision for every model measured, plus
`generate/eval-judges.ts`, which is how you re-measure when a new model appears.
It lives there rather than here because it answers *what this machine can run* —
a question about the hardware, not about this job. It is not repeated here; one
table that drifts is worse than one table you have to click through to.

What belongs to this job is the language, and one open question about the data.

Over 19 verses and 750 candidates, the two front-runners behave almost
identically apart from speed:

| model | language | accepted | rate | s/verse | incomplete answers |
|---|---|---|---|---|---|
| qwen3.6:35b | nb | 138/375 | 37% | **27** | 0 |
| qwen3.6:35b | en | 131/375 | 35% | **22** | 0 |
| qwen3.5:27b | nb | 147/375 | 39% | 118 | 0 |
| qwen3.5:27b | en | 133/375 | 35% | 97 | 1 |

Two things to read out of that. `qwen3.6:35b` is **not** the more selective judge
— an earlier two-verse sample suggested it was, and at nineteen verses the
acceptance rates are the same. And the sample deliberately favoured verses with
4–30 candidates, averaging 20 against the corpus median of 10, so a typical verse
runs faster than 22 seconds.

### Read the last column first

**`incomplete answers` decides whether the rest of the row means anything.** The
prompt asks for a verdict on all N candidates, in order. The schema cannot
require it — the array has no `minItems` — so it is a request, and a model is
free to answer about three of thirteen and return valid JSON. Measured with
`gemma4:31b` on John 3:16, thirteen candidates, the production prompt and schema
verbatim:

| schema | candidates | verdicts | time |
|---|---|---|---|
| the real one | 13 | **1** | 60 s |
| `id` + `accept` only | 13 | **14** | 11 s |

The call succeeded and the JSON was valid in both. Note that the deviation goes
both ways: fourteen verdicts for thirteen candidates.

A judge that answers about one candidate in thirteen and accepts that one scores
**1/13, 8%** on a row that counts candidates — and reads as the strictest judge
in the field. It was not strict; it did not answer. So the rate is computed
against **answered**, never against candidates, and both scripts now say how many
of each (#122). Had that single `gemma4:31b` verdict been an accept, the run
would now end:

```
Done. 1 verse, 13 candidates.
Answered: 1 (8% of candidates).
Accepted: 1 (100% of answered).
12 candidates unanswered across 1 verse — the model said nothing about them,
which is not the same as rejecting them.
```

The loss is not evenly spread. The failure mode is truncation at the end of
generation, so it is the *last* entries that go missing, and the candidate list
is sorted by descending similarity — the weakest candidates are hit hardest.
That softens the consequence, since those are the ones that would mostly have
been rejected anyway, but it makes the bias systematic rather than random. The
per-verse warning prints the missing ids as a range for exactly that reason: a
contiguous tail is the signature.

**What is still unmeasured is the one that matters: precision at this scale.** The
19-verse judging run failed in full on an expired API key, so the 549 accepted
references sitting in the data have never been scored — and scoring them is the
one measurement that could change the choice of judge. Everything the precision
column in running-jobs.md rests on is 72 references from two verses.

Language: judge in Norwegian, and not because of quality. The note the model
writes *becomes* the reference text in `references/nb`, so judging in English
yields English notes and needs a translation step. English was slightly stricter
and scored slightly higher in the small judged sample — not enough to pay for the
extra stage until it is confirmed.

### Things that cost a day to find out

Written down so the next comparison does not rediscover them.

- **`call()` returns a string.** `callWithRetry` is what parses the JSON. Reading
  `call`'s result as an object gives `undefined` for every field, which looks
  exactly like a model that answered nothing — two whole measurement rounds were
  scrapped before this was noticed.
- **Copy the prompt and you measure the copy.** A trimmed version of
  `buildVerifyPrompt` made two models return empty arrays. That is why it and
  `VERIFY_SCHEMA` are exported now, and why `eval-judges.ts` imports them.
- **Ollama keeps one model resident** unless `OLLAMA_MAX_LOADED_MODELS` says
  otherwise, so every model switch is a full reload. Warm-up first, then time.
  The penalty turned out to be only 5–6 seconds, but it is larger for larger
  models, so it biases the comparison in one direction.
- **`ollama` has no search command.** To find out whether a model name exists,
  POST it to `/api/pull` and abort the stream as soon as the manifest resolves:
  an unknown name errors in about two seconds and downloads nothing. Guessing
  names this way found 2 of 16 tried — poor coverage, but free. Reading
  `ollama.com/library` is the reliable route.
- **A newer, smaller sibling is not automatically better.** `qwen3.6:27b` is
  slower *and* takes more memory than `qwen3.6:35b`, because the 35b is a
  mixture-of-experts model that activates a fraction of its parameters.
- **Acceptance rate is not precision.** `aya:35b` accepted every candidate it was
  shown and looked, by count alone, like the most productive judge in the field.
  And it is not an acceptance rate at all unless the model answered about every
  candidate — see *Read the last column first*.

Two things do not travel between machines: `generate/embeddings/` is gitignored,
so the vectors must be rebuilt there with `--build-only` (cheap — `bge-m3` is
1.2 GB and fits anywhere), and the resume file lives in that same directory, so
two machines will redo each other's verses unless it is copied along.

## The order: search first, ask last

1. **Sweep what already exists** — free, no model.
2. **`references-semantic.ts` over everything.** Every reference it writes has an
   address taken from the corpus.
3. **Then look at what still has nothing**, and decide — deliberately — whether
   `references.ts` should fill those verses from the model's memory.

**Not the other way round, and the reason is `mergeReferences`: it never removes
anything.** Run the memory-based script first and its references become permanent
in *every* verse, including the ones where searching would have produced a
grounded answer. Run it last and the memory-derived material is confined to the
verses that had no alternative.

The tempting argument for the reverse — "8% of verses get no candidates at 0.65,
so searching cannot cover the corpus" — is true and proves the opposite. It is an
argument for asking *last, and only there*.

There is also something to protect. Most books have never been through
`references.ts`; only a minority have. Those untouched books can still become a
purely text-grounded reference set. The ones already processed cannot — the two
sources are merged in the same files with nothing marking which is which. What
order you choose now decides whether that stays possible.

## Sweep what exists first

```bash
bun generate/references.ts --validate            # report
bun generate/references.ts --validate --fix      # remove the dead ones
```

Free, no model. It applies the write-path gate to everything on disk and
separates two things that look alike:

- **dead** — the address exists in no numbering at all. `--fix` removes these.
  The write path now drops them as they are produced, so a sweep mostly confirms
  rather than finds.
- **renumber** — the reference is right but written in European numbering. `Mal
  4:5` does not exist here, because Malachi has three chapters, but it is `Mal
  3:23` and the reference is correct. These are **kept**; they are issue #40.

## The semantic pass

```bash
OLLAMA_MODEL=qwen3.6:35b bun generate/references-semantic.ts \
    --verify-only --resume --threshold 0.65
```

**`OLLAMA_MODEL` is not optional here, it is the whole difference.** Without it
the script asks for `qwen3.5:122b` — it passes `task: 'references'`, the same task
name the other script uses — and takes 96 seconds a verse instead of 22. Nothing
in the output says which model it got, so a run started without the pin looks
exactly like a run started with it, only four times longer. See *Choosing the
judge* above for what else was measured.

**When the run ends, read the unanswered count**, not just the accepted one. A
verse where the model left candidates without a verdict is recorded as such in
the progress file, and only those verses come back:

```bash
OLLAMA_MODEL=qwen3.6:35b bun generate/references-semantic.ts \
    --verify-only --resume --retry-incomplete --threshold 0.65
```

Two limits on that. Verses processed before 2026-08-03 carry no record either
way — they are marked done and `--retry-incomplete` does not reach them; a
verse-range run is the way back to those. And a re-run is only worth starting
with a different judge, or after a change: ask the same model the same question
and it will most likely leave the same candidates unanswered.

Nothing else on the command line should be there. Every flag that widens the
search buys references at a worse rate, and:

**Rank these by precision, not by yield.** A wrong cross-reference sends a reader
to a verse that has nothing to do with what they are reading, and nothing on the
page tells them so — in a project whose whole point is letting the reader judge
for himself, a fabricated connection undermines the one thing being offered. And
`mergeReferences` never removes anything, so a reference written today stays
until a human finds it. Volume can always be added later, by another pass with a
better model. Wrongness cannot be taken back. Three right references beat six
where two are wrong.

Measured by `generate/eval-references.ts` on six verses, scored 1–5 by Claude:

| flags | refs | score 1–2 | score 3 | share ≥4 |
|---|---|---|---|---|
| **`--threshold 0.65`** | 19 | **0** | 2 | **89%** |
| (defaults) | 20 | 0 | 3 | 85% |
| `--top-k 30 --threshold 0.65` | 44 | 1 | 8 | 80% |
| + `--concepts` | 45 | 1 | 8 | 80% |
| + `--theme` | 50 | 2 | 9 | 78% |
| + both | 51 | 2 | 8 | 80% |
| `--top-k 20 --threshold 0.65` | 35 | 1 | 7 | 77% |
| `--theme` (threshold 0.60) | 33 | 3 | 8 | 67% |
| `--top-k 20` (threshold 0.60) | 49 | 1 | 15 | 67% |

**`--threshold 0.65` and nothing else is the setting that won**, and it is the
one in the command above. Every widening flag scores below it; none of the nine
alternatives beats it on share ≥4.

The runs behind the table are the ten files in `generate/eval/`, all from
2026-05-10. **They are tracked, not gitignored, because they cannot be
regenerated** — the judge is Claude, so a re-run costs API credit and returns
its own numbers rather than these. `tests/eval-tabell.test.ts` reads them and
fails if a run ever beats the documented setting, so the sentence above cannot
quietly go stale. `results.json` is the file the script writes; the other nine
were copied aside by hand to keep the comparison. It is excluded from the table
because it is the only run over `EVAL_VERSES=extra` — four different verses, so
its numbers do not belong in the same column as the rest.

The threshold does the work. Raising it to 0.65 is what removes the crowd of
3-scores; widening `--top-k` past the default buys more references at a steadily
worse rate, and starts introducing outright errors. `--concepts` and `--theme`
both belong to the widening, not to the quality — they reach further, and what
they reach is weaker.

Threshold 0.70 has never been evaluated for quality. What it costs in coverage is
known, and it is steep. Measured over 2,078 verses — every fifteenth in the
corpus, no model involved, just cosine similarity over the vectors that already
exist:

| threshold | mean candidates | median | verses with **none** | hit the top-k cap of 30 |
|---|---|---|---|---|
| 0.60 | 25.2 | 30 | 1% | **72%** |
| 0.65 | 14.1 | 10 | 8% | 28% |
| 0.70 | 4.9 | 2 | **32%** | 6% |

Three things follow.

**At 0.60 the threshold does not bind.** Seventy-two per cent of verses hit the
top-k ceiling, so it is `--top-k` deciding what gets through — "the 30 nearest,
however weak." That is exactly why `--top-k 20` at 0.60 scored worst on
precision.

**At 0.70 a third of the Bible gets no candidates at all.** Precision bought
through the threshold has a hard coverage cost, and past some point the semantic
pass simply has nothing to say about a third of the verses, however good the
judge is.

**Which is the quantified reason the two scripts are complementary.** Not because
one decorates the other, but because vector search structurally finds nothing for
a large share of verses once you demand quality. Only `references.ts` has
anything to say about those.

Re-run the measurement with `topKByIndex` over the existing vectors; it takes
about two minutes and no GPU.

### Traps

- **Never `--force`.** It rebuilds the 127 MB vector file. The vectors already
  exist, and `--verify-only` skips the build anyway.
- **`--resume` is keyed by verse, not by parameters.** Verses already in
  `semantic_progress.json` are skipped forever, whatever settings produced them.
  To redo them with better parameters, remove their entries first.
- **`--skip-existing` skips every verse that already has a file** — which is the
  set where the merge has something to correct against. Use it only when you
  deliberately mean to fill gaps and nothing else.
- The vector file loads in 25 ms. When a run looks slow it is the model, not the
  data.

## Proofread

```bash
bun generate/references.ts --proofread --language nb --book 43 --chapter 1
```

This reads the actual Bible text ±2 verses around every reference, so it can see
that an address points at the wrong verse — the invisible class from the table
above, for references that were produced by asking rather than searching. It
writes its findings to `generate/proofread_references/<language>/...`.

Add `--apply` to write the corrections into the reference files. The findings are
saved either way — the trace and the fix are the same answer.

**The corrections are operations, not a rewritten list.** The proofread answers
with `corrections`: `remove` and `rewrite` against the `[N]` numbers in the list
it was given, `add` with an address and a text. Until #121 it was asked for
`revisedReferences` — the whole list again — and it echoed the input: 139 of 140
files address-identical to what they were given, 0 references removed, while the
same files reported 578 findings. A list can be echoed; a `remove` cannot, which
is why the field is gone rather than better worded.

What the code does with them: indices count from 1 and refer to the list as the
proofread received it, so removals don't shift the targets of later operations;
an index outside the list is skipped with a line, not applied to the wrong
reference; a new or re-addressed target goes through the same `checkTarget` gate
as a generated one, and an `add` that duplicates an address already present is
dropped. A reference nobody corrected is left alone even if its address is dead —
that is `--validate --fix`'s job, not the proofread's.

Proofread files written before #121 have only `revisedReferences`. `--apply`
reports them and writes nothing; run `--proofread` again to get corrections.

Two more things to know before running it at scale:

- There is no "only what already exists" mode. The loop generates first when a
  file is missing, so a proofread run over a range also *creates* every verse in
  that range that has no references yet — on Claude, and at Claude's price, if
  you forget `--local`.
- There is no resume marker. Reference files have nothing like the `checked`
  fields in the verse data, so an interrupted proofread starts over.
